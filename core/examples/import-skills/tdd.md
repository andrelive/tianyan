# 测试驱动开发（TDD 纪律）

**ID**: `tdd`

**版本**: 1.0.0

**描述**: 红→绿循环的参考标准：好测试的定义、seam 的选择、反模式与循环规则。

**状态**: 正式

## 适用场景

- 用户要求测试先行 / red-green-refactor 地构建功能或修 bug
- 需要写集成 / 回归测试时
- 评估既有测试是否值得保留、是否可靠

## 使用说明

### 好测试的定义

测试**通过公共接口验证行为**，不测实现细节。代码可以整体重写而测试不动。好测试读起来像规格（"用户可以用有效购物车结账"），且经得起重构（不关心内部结构）。

### Seam——测试放在哪里

**Seam = 观察行为的公共边界**；测试只活在 seam 上，绝不伸进内部。

**只在预确认的 seam 上写测试**：写任何测试前，先写下"被测 seam"并与用户确认。测试精力应落在关键路径与复杂逻辑（不可能什么都测——预确认 = 让测试精力落对地方）。

### 反模式

- **实现耦合**——mock 内部协作者、测私有方法、走侧信道验证（如绕接口直接查库）。判据：重构（行为不变）却弄坏测试。
- **同义反复**——断言按代码的方式重算期望值（`expect(add(a,b)).toBe(a+b)`、同法手推的快照、常量自证），构造上必过、永远不同义于 bug。期望值必须来自**独立的事实来源**（已知正确的字面量、手算样例、规格）。
- **横向切片**——先写全部测试再写全部实现。批量测试验证的是**想象的行为**：测到的是"形状"而不是用户可见行为，对真实变化迟钝。**改成垂直切片**：一条测试 → 一份实现 → 重复；每条测试是**曳光弹**，随上一轮学到的东西调整。

### 循环规则

- **红先于绿**：先写失败测试，再写刚好能过的最少代码。不为未来测试做预留、不加投机功能。
- **一次一片**：一个 seam、一条测试、一份最小实现。
- **重构不在循环内**：重构属于审查阶段（见 code-review 技能），不属于红→绿实现循环。

### 本地实例（天演语境）

- "反向验证"即 **red-capable** 纪律：新增 / 修改回归测试时，先注入旧行为证明它会红，再恢复修复——测试必须能抓住**这个具体 bug**。
- 期望值独立来源：如预算误报回归测试用**事故真实数字**复现，而不是按新实现重算。
