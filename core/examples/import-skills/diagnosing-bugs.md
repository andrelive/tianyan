# 缺陷诊断（Diagnosing Bugs）

**ID**: `diagnosing-bugs`

**版本**: 1.0.0

**描述**: 困难 bug 的诊断纪律——反馈回路先行、回路收紧、非确定性 bug 提频、无法建回路时明确停下。

**状态**: 正式

## 适用场景

- 排查任何"坏了 / 报错 / 失败 / 变慢"的问题（尤其硬 bug、间歇故障）
- 用户说"诊断一下 / debug 这个 / 查查为什么"
- 感觉"盯着代码看不出问题"时（这正是要停下来的信号）

## 使用说明

### 核心主张：反馈回路就是技能本身

有一根**在"这个 bug 上会变红"的紧回路，你就能定位根因**——bisect、假设验证、插桩都只是它的消费者；没有它，盯代码再久也救不了。**在回路上的投入要不成比例地多：激进、有创造力、拒绝放弃。**

构造回路的手段（大致按此顺序尝试）：

1. **失败测试**——能触达 bug 的任何接缝（单元 / 集成 / e2e）；
2. **curl / HTTP 脚本**——对着运行中的 dev server；
3. **CLI 调用**——固定输入，diff 输出与已知正常快照；
4. **无头浏览器脚本**（Playwright 等）——驱动 UI，断言 DOM / console / network；
5. **重放捕获的轨迹**——把真实请求 / 载荷 / 事件日志存盘，隔离重放；
6. **一次性 harness**——最小子系统（单服务、mock 依赖）单函数调用触达 bug 路径；
7. **属性 / 模糊循环**——"有时输出错"时跑大量随机输入找失败模式；
8. **bisect harness**——bug 出现在两个已知状态之间时，自动化"启动到状态 X → 检查 → 重复"，配 `git bisect run`；
9. **差分回路**——同一输入过旧版 / 新版（或两种配置），diff 输出；
10. **HITL bash 脚本**——最后手段（必须人点击时，让脚本驱动人，输出仍回流给你）。

### 收紧回路

把回路当产品：**更快**（缓存准备、跳过无关初始化、缩小测试范围）；**信号更尖锐**（断言用户的确切症状，不是"没崩"）；**更确定**（钉住时间、种子随机、隔离文件系统、冻结网络）。30 秒的 flaky 回路≈没有；2 秒确定回路是超能力。

### 非确定性 bug

目标不是干净的复现，而是**更高的复现率**：循环触发上百次、并行、加压力、缩小时序窗口、注入 sleep。50% 复现率可调试，1% 不可——先把频率拉上来。

### 建不出回路时

**明确停下并说清楚**：列出试过的手段，向用户要：(a) 能复现的环境访问权；(b) 捕获的工件（HAR、日志、core dump、带时间戳录屏）；(c) 加临时插桩的许可。**不要在没回路时进入假设阶段**——"直接跳到假设"正是本纪律要防的失败。

### 完成判据

回路**紧且红得起来**：你能说出**一条命令**（脚本路径 / 测试调用 / curl），**已经至少跑过一次**（贴调用与输出），并且：

- [ ] **红得起来**——驱动真实 bug 代码路径、断言**用户的确切症状**（能在这个 bug 上红、修好后绿），不是"运行不报错"；
- [ ] **确定**——每次运行同一结论（flaky 的按上文提频）；
- [ ] **快**——秒级，不是分钟级；
- [ ] **可无人执行**——你能独立跑（人在环只经 HITL 模板脚本）。

如果你发现自己在这个命令存在之前就开始读代码构建理论——**停下**。

### 本地实例（天演语境）

- grep 假阴性排查：**标记实验**（绝对路径 vs 相对路径 vs 缺省 path 对照）即"差分回路"的实例；
- 中止重复取证：DB 查询 + 服务端日志时序 + 单因子对照（真实消息重建请求抓 SSE）——"重放捕获轨迹 + 差分"组合；
- 无法复现时的正确收尾：写诊断探针 + 明确"下次复现请带证据"，不硬猜。
