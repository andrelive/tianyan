## 0.5.5 取消粒度修复（结构性取消 ADR-036）+ 长驻服务就绪即完成 + 轮级失败横幅

### 修复：取消粒度——「停止按钮有时按了没反应」（用户实测）

- **现象**：点「停止」后有时长时间无反应（最长 15s+），或看似没生效（输入区/停止按钮仍挂运行态）
- **根因（三处 await 盲区）**：取消置位链路已统一（停止端点 / 服务关停 / 唤醒轮同一会话槽），但响应侧只有同步检查点（3 处）——
  A. LLM 请求在飞（等待响应头/首块期间无信号传导；长思考模型 10–30s+）；
  B. 上下文组装 / 压缩（检索 / 压缩 LLM 调用无取消传导，15s 延迟实证）；
  C. 流式 recv 间隙（检查点在 `rx.recv()` **返回之后**——无新 chunk 时取消永不生效）
- **修法（统一语义：drop 即取消，ADR-036）**：
  - 新增 `agent::cancel` 等待原语：`wait_cancelled`（50ms 粒度，与工具执行层既有取消粒度一致）+ `cancellable`（select 竞争；**预置位快速路径不启动新工作**）
  - 五处等待点统一套用：流式请求发送 / 流式 recv / 组装 / 压缩（轮前+轮末）/ 非流式请求
  - model producer 补 `tx.closed()` select：接收端被取消 → 立即退出读取并断开连接（旧实现挂到下一块数据或 read_idle）
  - **收尾语义零新增**：全部走既有路径（已交付前缀 interrupted 落库 / `Cancelled` / 跳过压缩）——不回改已完成的轮结果；「外层 abort 整轮」被否决（REJECTED #21：丢失收尾语义）
  - 前端：「正在停止…」过渡横幅 + 停止按钮禁用态（点击 → 后端收尾完成 `turn_state idle` / 端点 `no_active_stream` 之间；纯内存态 + 20s 兜底）
- **判别力实证（先红后绿）**：recv 阻塞中取消（旧实现挂死）· 接收端 drop 后断连（旧实现等 read_idle=30s）· 轮末取消跳过压缩（旧实现必红）· cancel 原语 7 项——修复后全绿
- **演进预留**：0ms 信号级（Notify/watch）为后续计划——只改原语内部实现，五个调用点不动

### 修复：长驻服务卡唤醒（用户报告：启动后端服务+两个测试，因服务存续导致永远不唤醒收尾）

- **修法（B 方案「就绪即完成」）**：`CommandTask.counted` 新字段 + `release_wait_count`——就绪/探测超时释放待完成计数（幂等、触发唤醒）；终态递减只对 counted 任务。长驻服务不再算「待完成」
- **验证**：`test_ready_release_unblocks_wake_and_is_idempotent`；core 1322 全绿

### 新增：轮级失败持久横幅（LLM 请求失败不再「莫名中断」）

- error 事件置位会话级 `turnErrorBySession`（**纯前端内存态**：不落库、不污染 LLM 上下文、重启即清）——输入区上方持久横幅「上一轮中断：{原因}」；手动关闭或发送新消息后消失
- 验证：前端 421 全绿

### 内部

- `cargo fmt` 补齐——发布链路修复的格式化尾款（Quality 门禁 fmt check 恒红的根因）

## 0.5.4 多会话流式串扰修复（用户实测）+ 任务边界澄清

### 修复：跨会话流式串扰（写入寻址显式化）

- **现象**：多个会话并行流式时，**切进当前会话会刷出另一会话的流内容**（工具调用、思考、正文交错）（用户实测）
- **根因**：store 的隐式"当前会话"写入——`setMessages` / `deleteMessagesFrom` 不带 sessionId，把"写到哪里"绑定到 `currentSessionId`（随时间变化的全局状态）；切会话加载历史、回退操作的 `await` 期间跨越用户切换 → **写入错误会话**（数据库无污染，纯前端 store 层）
- **修复（原则：当前会话 = 视图选择 ≠ 数据寻址，写入只认实体 id）**：
  - 删除 `setMessages`（唯一写入路径 = `setSessionMessages(sessionId, …)`）
  - `deleteMessagesFrom` 加会话 id 参数；懒加载收口 `loadSessionHistory(sessionId)`（唯一入口：双重检查 + 流式中不覆盖）
  - 回退/重做在发起时捕获会话 id、`await` 后写回发起会话
  - `updateLastMessage` 加 role 守卫（只写最后一条 assistant——防"增量污染非 assistant 消息"放大器）
- **判别力实证（先红后绿 ×3）**：慢历史加载 + 中途切换 → 迟到响应污染新会话（修复前红）；回退请求挂起 + 切走 → 回退结果写错会话（修复前红）；末条为 system 时增量写入（修复前红）——修复后全绿
- **验证**：前端 56 文件 / 420 测试全绿；typecheck 通过；lint（eslint + prettier）干净

### 文档：任务边界澄清（防漂移）

- **命令任务有意不持久化**：命令类任务（`CommandManager`）纯进程内存（`MAX_RETAINED_TASKS=100` 逐出最旧非 Running），**重启即清空、属预期行为**——长会话会累积大量前后台命令，全部落库、长期可见会争夺用户注意力（委托任务走 SQL，可跨重启恢复，不变）
- **任务面板有意会话级**：只显示当前会话任务（切换会话隐藏/恢复）；不做跨会话聚合——其它会话任务不进入视野
- 落点：ADR-026 §4/§5「D 边界澄清」、ADR-013 交叉引用、module-map、三处代码注释

## 0.5.3 跨会话压缩摘要串号修复（用户实测取证）+ T1 审计批次 + 质量门禁收敛

### 修复：跨会话压缩摘要串号（用户实测取证）

- **现象**：会话 B 的压缩点摘要里混进了**会话 A 的整段历史**，并作为「对话摘要」落库——此后每一轮都被注入模型上下文（用户从数据库取证：污染点摘要同时包含两个会话的内容，A 的记录被当成 B 的主线）
- **根因**：`ContextCompressor` 的 `cached_summary` 是**进程级**可变状态，不按会话隔离。A 会话压缩后把摘要缓存下来，B 会话压缩时这个缓存被当作 `existing_summary` 拿去做增量合并——A 的历史就这样被并进了 B 的摘要
- **修复（数据源单一化，彻底删缓存）**：删除 `cached_summary` / `cacheable_summary`，压缩器变成**无会话状态**；「已有摘要」改由调用方从**当前会话链最后一个压缩点（`compression_marker`）**读取（`extract_marker_summary` 剥掉展示包装），显式传进压缩函数；压缩器自身的 `compress()` 永远走全量摘要。空摘要语义保留（空结果不落库 → 天然不会成为「已有摘要」）
- **判别力实证（先红后绿）**：新增 `test_cross_session_compress_does_not_reuse_previous_summary`（A 会话含唯一标识串）——修复前**红**（B 的压缩请求继承了 A 的摘要），修复后**绿**
- **同型「进程级共享可变状态」复核**：`cached_soul`（soul 全局单例，语义正确无须隔离）· `injectable_context` / `injectable_snapshot`（已按会话 + 会话头持久化，ADR-012）· `pending_approval_fingerprints`（仅审批面板展示，不进模型上下文）
- **历史数据**：污染摘要 `cmp_1789711775947` 按用户指示**保持原样**，本次不做清理

## 0.5.2 退出机制优化（用户报告）+ 工具执行可取消 + T1-11

### 修复：退出卡死——托盘/进程残留（用户报告）

- **现象**：点托盘退出后图标与进程残留（任务管理器剩 webview + cargo 子进程），只能强杀收场；此前"后台任务跑着时退出"同款
- **根因（三条链叠加）**：① 关停只置位 `shutdown_flag`，其唯一消费者是 `/tasks/stream`——正在跑 agent 轮的 `/chat/stream` 不读它 → **axum 优雅关停死等活跃连接**；② `server_handle.await` 与 tauri 监督等待均无上限 → 监督循环不结束 → **`app_handle.exit(0)` 根本不执行**（日志"退出应用"是假象，后面已无代码）；③ Windows 无 Job Object 绑定，父进程退出不带走子进程
- **修复（按"退出时主动中止、不等任务跑完"）**：关停先**主动中止所有活动轮**（遍历会话取消槽全部置位——配合工具执行可取消，跑到一半的命令会被杀）→ **统一清理前后台子进程**（全局注册表 + `ChildGuard` 自动注销 + 按进程树清理）→ **超时兜底**（server 侧 5s / tauri 侧 10s 强制继续退出）——无论有没有任务在跑，都保证退出

### 修复：「停止」无法中断正在跑的命令（用户报告）

- **现象**：长命令（如 cargo 构建）执行期间点「停止」毫无反应，界面卡在运行中只能陪等
- **根因**：取消检查点只在轮顶与流式 chunk 循环；工具执行路径完全不读取消标志
- **修复**：`execute_command_action_cancellable` 以 `tokio::select!` 三路竞争（正常退出 / 超时 / **取消**），取消即**杀进程树**并返回「命令已取消」（与超时分开）；工具层从会话取消槽取标志——「停止」按钮置位的正是它

### 修复：刷盘先清零后落盘（T1-11）

- `usage_stats::flush` 先 `swap(0)` 清空内存计数器再落库：落盘失败即丢整批统计；`trace::flush` 同形态（一批 span 永久丢失）。改为「读快照 → 落盘成功 → 才扣减」；trace 失败把 span 放回缓冲（顺序保持）

### 修复：CI 构建失败（quality.yml）

- Linux runner 上 lance-encoding 构建脚本找不到 `protoc`（release.yml 有安装步骤、quality.yml 漏配）→ 补 `arduino/setup-protoc@v3`

### 验证

- core **1308**（+5 回归）· server 164 · tauri 13 · mcp 16 · 前端 414；clippy 0（workspace 全目标）/ fmt 干净
- **判别力实证**：取消注入"不响应" → 红（29.6s 才返回）；注册注入"不注册" → 红；T1-11 双注入 → 2 红；均已还原复绿

## 0.5.1 分段加载页边界对齐 + apply_patch 静默错位修复

### 修复：长会话上滚时工具卡"假运行中"（用户实测发现）

- **现象**：长会话上滚翻页时，页边界处出现**"运行中"转圈的历史工具卡**（实为早已完成）+ 旁边一个无归属的"工具结果"卡
- **根因（数据实证）**：会话历史按 50 条硬切分页，而"工具调用 → 其结果"是相邻两条消息——**约 50% 的页边界恰好切在这对之间**（全链 4633 条实测：92 个页界 **46 命中**）。含结果的页没有调用 → 结果只能作为"孤立卡片"显示；含调用的页没有结果 → 卡片 `result=null` → 前端按"未完成"渲染成"运行中"
- **修复（页边界对齐用户消息）**：以 50 条为基准取窗口 → 页从「窗口内由远及近第一条**用户消息**」起（截取）；窗口内没有 → **直接向前找最近一条更早的用户消息**（一次查询，不按批扩展、不设人为上限）；到链头仍无则整段兜底。**页首恒为用户消息** → 工具调用与其结果不会被分页切开
- **效果（全链模拟 4633 条）**：跨页"调用|结果"对 **46 处 → 0**；页首=用户消息 **56/56**；上滚拼接覆盖 **100%**（无缺无重）；页大小随"轮"浮动（1~446，平均 83）
- **附带体验**：每页从用户消息开始，**因果关系完整**（上滚时总能看到"这一轮是从哪句话开始的"）

### 修复：apply_patch 静默错位（工具实现缺陷）

- **现象**：补丁块内含空行上下文时，新增内容被插到**上一行之后**（例如插到函数闭合 `}` 之前）——**代码语法被破坏却没有任何报错**
- **根因（两层，已定性并留回归）**：① 解析层把「一个空格」的**显式空上下文行**当成"文件级空行"丢弃（与代码注释声称的语义矛盾）→ 期望匹配窗口少一行；② 定位层的模糊匹配在精确匹配失败后采用"相似度达标"的窗口——而"整体平移一行"的窗口相似度同样可能达标 → **静默改错位置**
- **修复**：① 只忽略**完全空行**（空上下文行是有效信息，必须参与匹配）；② 新增**位置敏感守卫**（逐位置比较非空行的匹配率）——拒绝"整体平移一行"，同时保留"个别行抄写误差"的容错；守卫不通过时**报"无法定位补丁块"**（可见失败，绝不静默改错位置）
- **顺带**：清理僵尸依赖声明 `diffy`（此前已移除、残留声明）

### 修复：后台任务通知前端不实时显示（用户报告）

- **现象**：后台任务/命令完成的通知气泡不再实时出现在会话里（刷新/重连后能看到——它在库里，只是没推）
- **根因**：ADR-028 的「落库即推送」挂在 `SessionManager` 包装层，而 0.5.0 的"写侧收口"把**所有写入**改走会话工作集（`ws.append` 直写库）——**包装层不再是入口** → 通知与压缩点落库后不再广播。（用户消息靠前端乐观渲染、assistant/工具结果靠流式推送，所以只有"通知"暴露；0.3.12 的"压缩点实时推送"同源受影响，一并修复）
- **修复**：把边界消息（System 通知 / 压缩点）的推送挂到工作集落库路径（工作集现在就是唯一写入口）——同一门控、同一映射；core 仍不感知通道（回调由装配层注入）

### 增补修复（本轮收尾）—— T1 清单剩余项 + 死配置接线

- **后台命令并发上限失效（T1-5）**：`_permit` 是 `spawn_background` 的局部变量，函数返回即 drop（**提前释放**）——命令仍在运行但许可已归还，ADR-026 的「16 并发」上限形同虚设。修复：`OwnedSemaphorePermit` **移交 watcher 任务持有**，随命令真正结束（进程退出 → 收输出泵 → 落终态 → 通知）释放

## 0.5.0 会话工作集（架构级）—— 会话上下文不再每轮全量重建 + U10 唤醒轮三症状修复

> 本版为**架构级**更新（ADR-035）。用户可见变化集中在「唤醒轮」（后台任务/通知触发的自动轮）：**可停止**、**状态可见**、**消息顺序与库一致**；其余为会话链路的内部重构（不改功能语义，无需用户操作）。

### 架构：会话工作集（ADR-035）

- **旧问题**：每一轮（用户轮 / 唤醒轮）都把整段会话历史从 SQLite 重新读出、重新组装、重算前缀——历史越长越慢，前缀缓存命中越差；且写入路径分散（server 会话 API / agent 层 / 通知器各自直连 `SessionManager`），一致性靠"每轮重建"兜底——`MAX(seq)` 是弱信号（`rewrite` 等长 / 写操作相互抵消 / 仅 header 变化都检测不到），属"靠巧合工作"
- **新机制**：引入**会话工作集**（`SessionWorkingSet`，键 = 会话 id）——会话的物化上下文缓存。定位：**非第二权威**（权威仍是 SQLite，ADR-018/027 不变）、**非新存储**、不引入第二把锁；只物化「**最近压缩点 → 现在**」这一段，段外（压缩点之前）经库按需读；空闲 30 分钟卸载，重建点 = 最近压缩点；连续轮 / 唤醒轮复用同一份段
- **写入收口（单一写入口）**：追加 / 整表重写 / 头部更新 / 删除四类写入全部经工作集（先落库 → 再更缓存 → 再派发）；`SessionsService` 五个活跃写路径 + agent 层落库 + 三处历史旁路（演化会话清理 / 定时任务会话重建 / 会话 header 更新）全部收口；`ensure_fresh` 降级为**架构违规探测器**（warn + 重建兜底）
- **续跑判定取代"通知投递水位"**：不再有"投递"这个动作——本轮组装所见库尾（`ctx.last_seq`）与工作集所见库尾（`ws.last_seq`）不一致即说明有新消息，**本轮自行消化**（增量注入后续 turn，不入队、不唤醒）。水位三件套连同"重放"路径整体删除 → **T1-24（重启重放历史通知）机制性消失**
- **唤醒幂等**：同一会话 N 条并发通知**只产生 1 轮唤醒**——"已有轮在跑"的判定与"轮收尾退出"的判定在**同一临界区**，不存在"判定无新消息 → 退出"与"通知刚到"之间的丢通知窗口；已有轮在跑时通知落库即被该轮消化
- **顺带修掉一处真实竞态**：旧 `update_session` 用 server 侧旧 header 整体覆盖，会丢掉刚固化的注入快照

### U10 唤醒轮三症状修复（用户报告）

- **停不掉**：唤醒轮此前**没有取消槽**（`cancel: None`）——"停止"按钮对它完全无效。现唤醒轮注册会话取消槽，`/chat/streams/{id}/cancel` 无用户流时经 `Agent::cancel_active_turn` 置位

- **快照键统一到消息 ID**：`capture` / `restore` / `diff` / `load_tree` 的键从"数字位置"改为**消息 ID**——位置会随压缩/回退重排，ID 稳定；捕获时机挪到用户消息落库后（消除"内存条数 == 位置"的隐式等式）

- **无老会话兼容**：按决定不做迁移（存量会话首轮自动按工作集语义重建），无需用户操作

## 0.4.7 唤醒风暴修复（通知投递事务化）+ T1 四项加固

### 修复：后台任务唤醒风暴（T1-23，用户报告）

- **现象（数据实证）**：脚手架会话主轮 11:47:01 正常收尾后，3.5 分钟内连跑 **9 轮唤醒**，每轮重复汇报同一批 5 个失败（模型自己都写“已在前两轮逐条汇报”“本轮不再重复表格”）；过程中用户还看到“右侧任务已完成、主会话无反应”
- **根因**：① 上下文在本轮启动时组装一次，turn 之间**不重读历史**——活动轮期间落库的通知（就绪/完成/失败）只能等下一个 loop 才被读到（故主轮看不到、收尾汇报也没提那些失败）；② 这些事件各自 wake 并被 turn_guard 排队，主轮一结束后逐个开跑，每个都重读**同一批**历史通知又被指令要求“必须汇报”→ 重复 9 遍（“通知只落一次，却被读了 9 次”）
- **修复（对齐 ADR-013“消息入库 + 轮次边界投递”）**：
  - **轮边界增量投递**：每个 turn 开始前把水位之后的新通知尾部追加进上下文（前缀不变 → 缓存友好）→ 活动轮自行消化，模型下一 turn 就看到；
  - **投递水位（恰好一次）**：投递与水位推进同一临界区完成（会话轮互斥）；唤醒轮组装前记水位上界、组装后推进（组装与推进之间新落库的仍 pending，不丢不重）；
  - **条件唤醒**：轮收尾若“仍有未投递通知”→ 补一轮（覆盖“通知恰好落在最后一 turn”的边界）；唤醒入口同判定 → 已被活动轮消化的排队唤醒**直接跳过**（9 轮 → 0~1 轮）。逐条唤醒 / 就绪唤醒 / 通知带指令三者保持不变

### T1 四项加固（T1-1 ~ T1-4）

- **T1-1 run_tests/verify_build 缺省 cwd**：缺省 cwd 落**进程目录**（桌面=安装目录）→ 项目探测与执行都在错误目录；现缺省即**会话工作目录**，沙箱/审批/执行同一口径
- **T1-2 唤醒轮失败判定**：任一会话、任一 3 天内的历史失败都会让本会话唤醒指令变成“必须汇报失败”；现限定**本会话 + 1 小时时间窗**
- **T1-3 task_cancel 真正终止执行**：取消只改面板状态（子代理继续烧 token / 占运行许可）；现协作标志 + `AbortHandle` 兜底硬中断
- **T1-4 显式 namespace 检索**：`retrieve_by_namespace` 先走意图检索再过滤——意图把范围限到别 namespace 时 rules/memories **静默为空**；现 namespace 直接下推 VFS 搜索

- **唤醒轮输出不实时显示（需退出重进才看到）**：根因 = 唤醒轮转发器先 `await` 整个 `process_wake` 完成才去取事件——期间事件持续写入容量 100 的通道，输出超过缓冲即阻塞，形成死锁（轮等转发器收、转发器等轮完）。修复 = `process_wake` 改收 `sender` 参数（与 `process_message_stream` 同构），转发器在轮开始前就建通道并立即消费；新增防死锁回归测试
- **流式事件转发三处接线收敛为单一实现（ADR-032）**："chunk → 事件 JSON → 统一通道"的接线原在用户轮 / 唤醒轮 / 子代理三处手写，已出现漂移（容量 100/100/64 不统一、字段注入各写一遍）——上述死锁 bug 正是该结构的产物。core 新增 `agent/stream_forward.rs`：`spawn_stream_forwarder` 原子地建通道并启动消费任务（反向顺序从结构上写不出来），`StreamEventMapper` / `StreamEventDeliver` 保留为可插拔 seam（映射器与送达目标），`inject_stream_event_fields` 单点注入路由字段。三处调用点复用该函数
- **ollama 思考字段回传（传输层方言）**：0.2.7 只修了"读"（`DeltaContent` 加 serde alias `reasoning`）没修"写"——`inject_reasoning_content` 把历史思考无条件写到 `reasoning_content`，而 ollama 的 OpenAI 兼容层（`openai/openai.go` 的 `Message.Reasoning`）**只解析 `reasoning`**。Go 的 `encoding/json` 静默忽略未知字段，所以请求照样成功，但思考内容根本没进 prompt——多轮上下文与思考一致性悄悄受损（实测：ollama cloud 上 `reasoning_content` 的 `prompt_tokens` 零增长，`reasoning` 则 +2300）。修复 = 新增 `ThinkingField` 方言（`ReasoningContent`/`Ollama`），在客户端构造时按「显式配置 > endpoint/名称嗅探 > 默认」解析一次并缓存，`inject_reasoning_content` 按方言写字段名（互斥不双写）；新增 `thinking_field` 配置项作为嗅探不到的网关的逃生门（嗅探只认 ollama 域名与 `:11434`，刻意不猜自建域名）
- **前端配置往返丢弃 provider 新字段**：根因 = 前端 `config-transform.ts` 对 provider 是白名单映射，而后端 `PUT /api/v1/config` 是全量替换——后端新增的 provider 级字段（`thinking_field`）不在白名单里，用户按文档手写进 `tianyan.toml` 后，只要打开设置页点一次"保存"就被静默抹掉。修复 = 双向透传 + 设置页新增「思考字段名」下拉（自动 / `reasoning_content` / `reasoning`）；契约测试新增通用防线（逐字段断言 provider 每个键都能往返），防止下一个新增字段重蹈覆辙

- **修复**：新增 `StreamEventSender::send_turn_usage`（delta 空、is_complete=false，前端归约器只消费 usage 字段附加到最后一条 assistant 消息，无正文/边界副作用）；`handle_llm_response` 工具轮分支在 persist 后逐轮下发该轮 usage——前端本地消息每轮都带 usage，会话消耗汇总恢复为真实总量（回归测试锁定工具轮事件下发）

## 0.2.9 修复（托盘退出卡死：常驻 SSE 流阻塞优雅关停）

- **根因**：`GET /tasks/stream`（后台任务聚合 SSE，ADR-026）的 forwarder 死等 broadcast 消息，无任何退出条件；前端 `AgentTasksPanel` 用 EventSource 常驻订阅该流（会话存在期间不关闭）。托盘「退出」→ `app.exit(0)` → ExitRequested 钩子 `prevent_exit` 后 `rt.block_on` 等待内嵌 server 优雅关停 → axum `with_graceful_shutdown` 等待所有活跃连接结束 → 常驻 SSE 连接永不结束 → 进程卡死，只能杀进程
- **修复**：`stream_tasks` forwarder 加 shutdown 感知（与 `/chat/stream` 的 `spawn_sse_forwarder` 同模式）——`tokio::select!` 轮询 `shutdown_flag`（1s 间隔），置位即结束流，优雅关停链得以完成（约 1-2 秒内退出）
- **约束**：任何新增常驻 SSE 端点必须带 shutdown 感知，否则阻塞应用退出（已写入 ADR-026）

## 0.2.8 修复（流式 usage 丢失根因：请求未显式要求 + 尾块被丢弃）

- **根因**：0.2.7 的 usage 兜底只是"症状缓解"——真正的根因是两条叠加的链路缺陷：① 流式请求从未发送 `stream_options: {include_usage: true}`（OpenAI 规范：流式响应默认不返回 usage，除非请求显式要求）——ollama 等严格遵守规范的网关因此永远不返回 usage，0.2.7 之前实测"ollama 流式不返回 usage"其实是没向网关要；② SSE 解析把 `{"choices":[],"usage":{...}}` 尾块（include_usage=true 的正常流尾）当作"正常流尾"静默丢弃——即使网关返回了 usage 也会丢掉
- **流式请求显式要求 usage**：`chat_completion_stream` 构造请求时设置 `stream_options: {include_usage: true}`（对齐 DSH 同名参数，回归测试锁定请求体含该字段）
- **usage-only 尾块保留下发**：SSE 解析识别 `{"choices":[],"usage":{...}}` 块后构造带 usage 的空 chunk 下发（loop 收到后更新 `last_input_usage` 校准值），不再静默丢弃；纯 cost 块（兼容层 `{"choices":[],"cost":"..."}`）、无 choices 无 usage 的空块仍正常跳过（回归测试锁定两种形态）
- **思考内容正确回传**（DeepSeek 官方要求）：携带 tools 的请求必须完整回传 `reasoning_content`（即使该轮未实际进行工具调用，官方 thinking_mode 文档）——`convert_messages` 此前用 `..Default::default()` 构造 assistant 消息（async-openai 0.34 无此字段），序列化后被静默丢弃；改为序列化后按索引回填（`inject_reasoning_content`，非流式与流式统一走 JSON 层）；`assembler` 去掉 `has_tool_calls` 条件无条件保留 reasoning（回归测试锁定无工具调用轮也保留）
- **估算计入思考与工具参数**：`TokenEstimator.estimate_message` 此前只算 `message.content`，漏掉 reasoning_content 与 tool_calls 参数——思考十几万字的会话被低估（5% 显示的根因之一）；估算纳入思考内容与工具调用参数（回归测试锁定），无 usage 兜底时占用显示包含思考
- **换模型旧实测值失效**：`last_input_usage` 从裸数字升级为 `(model, tokens)` 配对——同一会话切换 provider/model 后旧实测值不再适用（不同模型分词/计费口径不同），退回全量估算（对齐 DSH token-meter：header 不匹配时全量重估）（回归测试锁定）

## 0.2.7 修复（ollama 网关兼容：思考过程不显示 + 上下文圆环无数据）

- **根因**：聊天模型切换到 ollama 提供商（deepseek-v4-flash:0731）后，两个功能同时失效——ollama 兼容层流式响应与 opencode 网关存在两处协议差异：思考字段名不同（`delta.reasoning` vs `delta.reasoning_content`）、流式 chunk 不携带 usage（非流式才返回）
- **思考过程兼容**：`DeltaContent.reasoning_content` 加 serde alias `reasoning`，统一解析 ollama 与 DeepSeek 两种字段名（回归测试锁定）
- **流式 usage 兜底**（对齐 DSH token-meter 启发式）：网关不返回 usage 时用 TokenEstimator 估算（prompt 优先用上次实测值，completion 按正文+思考估算）——上下文占用/缓存命中展示与压缩判定不因网关差异而失效；真实 usage 存在时不受影响

## 0.2.6 修复（后台任务与子智能体统一面板，ADR-026）

## 0.2.5 修复（todo 工具批量语义 + 完成条目保留展示）

- **批量操作**：todo 工具 create 接受 todos 数组一次写整份清单（不再逐条调用）；update 接受 updates 数组一次合并多条状态变更（开始/完成多条一次调用）；delete 接受 ids 数组；单条形态保留兼容。存储层 create_many/update_many/delete_many 单次落盘，update 原子（任一 id 不存在整体不上盘）
- **子待办**：parent_id 挂靠父待办（校验父存在且属于本会话），面板缩进展示——发现新工作/拆子任务随时追加
- **修复「todo 不存在或不属于当前会话」误报根因**：存储懒加载竞态——create/update/delete 不触发磁盘加载，新进程首个 create 会把既有条目全部覆盖；读盘移入写锁内双重检查（ensure_loaded）
- **修复后台终端命令对面板不可见**：execute_command(background) 启动的后台命令（cmd_*）只存在于 agent 内部注册表（task_status 可查），「后台任务」面板读的是委托任务注册表——实测"明明有后台实验在跑，面板却空空如也"。合并两套注册表为统一视图（BackgroundTask::from_command_task），面板显示终端/委托类型徽标，取消按钮对终端命令走进程树终止
- **修复整点定时任务触发的整进程闪退**（8/29 20:00、8/30 20:00、8/31 14:00 三次，WER BEX64 fail-fast）：根因链 = 摘要任务（cron 0 0 */6 * * *，UTC 语义 = 本地 8/14/20/2 点）发现待摘要条目 → 嵌入请求未携带 dimensions 参数（API 按模型默认 1024 维返回）→ 写入 LanceDB 时与配置 vector_dimension(3072) 的建表维度不一致 → arrow FixedSizeList 内部 panic → release panic=abort 整进程即刻终止且日志无任何输出。修复：嵌入路径按向量库建表维度显式请求 dimensions（index_entry 与查询路径，VectorStorage 新增 embedding_dim 声明）；upsert/查询前置维度校验，不匹配转为带行动指引的干净错误（回归测试锁定），杜绝此类 panic 再次发生
- **调度模型从 cron 改为间隔 + 补跑（ADR-024）**：个人 PC 服务不常驻，cron「某时刻执行」宕机即永不执行且 UTC 语义造成本地触发时刻漂移。改为间隔制——任务声明执行间隔，单一扫描循环每 60 秒顺序检查，「距上次执行 ≥ 间隔」立即执行；last_run 持久化（scheduler_state.json），宕机超期任务重启后自动补跑一次；全任务串行消除资源争抢；顺带修复边界双跑 bug（每任务在整点 ±1s 各执行一次）。用户自建定时任务同步迁移（旧 cron 自动换算），schedule_task 工具与「定时任务」创建表单改为间隔语义
- **完成条目保留展示**：面板不再过滤已完成条目——划线 + 对勾保留展示（可回看），无任何条目后面板才消失
- **面板宽度对齐输入框**（max-w-4xl 居中，与 composer 一致）

详见 [ADR-022 修订](../architecture/decisions/022-session-bound-task-ux.md)。

## 0.2.4 修复（流式静默中断，断流根因排查）

- **根因确认**：断流为 opencode 网关→GLM 上游连接中断（网关以非标准 finish_reason=network_error 结束流），DSH 同模型同供应商同样复现——非天演独有；但天演此前叠加了两个自身问题使断流"静默化"

- **network_error 结尾块被静默丢弃**：非标准 finish_reason 反序列化失败即跳过 → 显式上抛并携带原始原因（与 DSH 报错可见性对齐）

- **文件日志 0 字节**：文件层与 RUST_LOG 解耦，GUI 实例日志不再静默归零
- **输出上限链路确认**：设置页模型 output 限额（max_output_tokens）经 T6 动态预算正确生效（请求 max_tokens = min(配置值, 上下文预算)），前端 2048 参数不参与

### 分层重构（阶段 1-3）
- **基础类型层**：`roles`（角色纯类型）、`common`（含 RetrievalTrace）——config/agent/scheduler 共用，打破 `config↔agent`、`scheduler↔agent` 环
- **统一写入门面**（ADR-020）：`db::Database` 门面（单连接 + schema 集中）+ 业务域 Repository（stats/trace/execution/usage）；8 个组件不再各自持 SqliteDb
- **SQL 收敛**：Session/Stats/Trace/Execution/Usage 五域数据访问收口到 Repository/本模块（会话专属存储归 ADR-018）
- **db 纯底层**：SqliteDb 移入 db、SessionRepo 归位 session、RetrievalTrace 引用 common——**生产代码零模块环**（文件级 SCC = 0）
- **依赖清理**：cargo-machete 移除 7 个未使用依赖（core: anyhow/clap/diffy；server: tracing-subscriber；tauri: tower/tower-http/uuid）

## 0.1 主要功能（回顾）

### 智能体
- **对话与工具调用**：流式响应、思考过程、工具调用（文件/代码/搜索/网络/委托/定时任务）
- **编辑链路**：`apply_patch`（主力，unified diff + 上下文锚定，对齐 omo/Codex）+ `apply_edit`（内容匹配，极小改动）
- **子代理委托**：并行/嵌套委托（深度上限 3）、后台任务、完成通知
- **定时任务**：真实 cron 语义，可安排周期性工作

### 知识体系（VFS）
- **统一存储**：文档/记忆/规则/技能全部经 VFS（L0/L1/L2 双层摘要 + 向量检索）
- **自动注入**：soul/rules/memories 前缀按查询检索注入（会话首轮冻结，命中前缀缓存）
- **按需检索**：`search_vfs` 语义搜索整个 VFS（文档/记忆/规则/技能）
- **自进化**：技能/规则随使用自动学习（GEPA）

### 桌面应用
- **托盘常驻**：关窗最小化到托盘，后台任务继续运行；`Ctrl+Alt+T` 唤起
- **系统通知**：后台任务完成/审批挂起/主动提醒 → 桌面通知
- **剪贴板**：监听捕获 + agent 写出
- **自动更新**：启动检查 GitHub Releases，用户确认后安装

### 工作区
- 文件树/查看器/编辑、diff 面板、LSP 诊断、测试发现、构建验证

## 安装与使用

### 桌面应用（Tauri）
1. 从 GitHub Releases 下载安装包（`Tianyan_<版本>_x64_zh-CN.msi` / `Tianyan_<版本>_x64_en-US.msi`）
2. 首次运行 SmartScreen 警告时点"仍要运行"（安装包**未做代码签名**；updater 的 `.sig` 是 Tauri 更新签名，与 Windows 代码签名无关）
3. 启动后自动检查更新

### 本地服务（开发模式）
```powershell
cargo run -p tianyan-server   # 后端 http://127.0.0.1:3000
cd gui-vite && npm run dev    # 前端 http://localhost:5100
```

### 配置
- 配置文件：`tianyan.toml`（模型 Provider/Model、存储、安全、日志、Web 搜索）
- 数据目录：`~/.tianyan`（SQLite 会话 + VFS 内容 + 快照）

## 发布流程（维护者）

1. 更新版本号（workspace Cargo.toml / tauri.conf.json / gui-vite package.json）
2. 推送 `v0.2.0` 标签触发 GitHub Actions 发布流水线
3. 流水线产出 `.msi` + `.sig` + `latest.json` 上传到 GitHub Release
4. 用户启动应用时自动检查更新
