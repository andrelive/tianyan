## 三、重编带基线（incremental = OFF，现状默认）

三场景各 `touch` 一次（只改 mtime，不改内容），`cargo build --workspace`：

| 场景 | 目标文件 | 重编 crate | 重编源码行 | 占比 | 墙钟 |
|---|---|---|---|---|---|
| 改一个工具 | `core/src/executor/web.rs` | core + server + mcp + tauri | **63,999** | **100%** | 106.7s |
| 改内核机制 | `core/src/agent/loop.rs` | 同上 | **63,999** | **100%** | 93.3s |
| 改 S 级契约 | `core/src/common/types/uri.rs` | 同上 | **63,999** | **100%** | 86.9s |

**结论 1：三种改动完全等价，都是整核全量重编。** 这从数据上证实了 ADR-049 的核心判断 ——
现状瓶颈不是"某个模块太大"，而是**没有编译边界**（rustc 的编译单元是 crate，crate 内模块边界对成本零作用）。

> 时间抖动说明：同一场景在不同负载下测到 61.9s / 86.9s / 106.7s（±30%）。
> 因此**判据以「重编行数」为主指标、墙钟为辅**——行数是编译图的确定性质，不受机器负载影响。

## 四、incremental 实验（`CARGO_INCREMENTAL=1`）

同一脚本、同一三场景，仅打开增量编译：

| 场景 | incremental OFF | incremental ON | 加速比 | 重编行数（ON） |
|---|---|---|---|---|
| 改工具 `web.rs` | 106.7s | **31.4s** | **3.40×** | 64,328（仍 100%） |
| 改机制 `loop.rs` | 93.3s | **31.9s** | **2.93×** | 64,328（仍 100%） |
| 改契约 `uri.rs` | 86.9s | **33.8s** | **2.57×** | 64,328（仍 100%） |

**磁盘代价**：`target/debug/incremental` = **7 个会话 / 1,297.9 MB**（约 **185 MB / 编译会话**）。
按每天 20 次编译估算 ≈ **3.7 GB/天** —— 这正是 2026-09-21 累积 1,203 个会话 / 179 GB 事故的成因。

### 结论 2：incremental 与拆 crate 优化的是**不同维度**

| 维度 | incremental | 拆 crate |
|---|---|---|
| 重编**行数** | 不变（仍 100%） | **降到 5% 以下** |
| 重编**时间** | 降 ~3×（复用 query 缓存） | 降 ~20–30×（少编译 95% 代码） |
| 磁盘代价 | +185 MB / 会话（需 GC） | 无额外 |
| 语义风险 | 无（只是编译优化） | 迁移期双路径 |

**所以两者互补，不能互相替代**：incremental 是"少算重复的"，拆 crate 是"少算该跳过的"。
期 0 的结论是**同时要**，但顺序必须是先拆（决定行数），再把 incremental 作为日常开发加速。

### 建议（期 0.5 执行）

1. **开启 `incremental = true`**（dev profile），配套 GC：
   - 保留最近 3 天；总大小上限 20 GB；超限按 mtime 从旧到新删除
   - **CI 永不开启**（runner 是一次性的，纯浪费磁盘与时间）
   - GC 挂在已有的 `GcTask`（调度器）里，或作为 `scripts/` 独立脚本 + 启动时检查
2. 理由：3× 的日常开发加速值得 185MB/会话的成本，前提是**有 GC 兜底**（否则复现历史事故）。
3. GC 落地前，默认仍保持 `incremental = false`（现状）。
