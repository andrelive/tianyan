# ADR-044: 流式双预算——首 token 预算与块间空闲分离

**日期**: 2026-09-25
**状态**: ✅ 已落地
**修订**: ADR-023 之后的「读空闲超时」修正（本次把**单一预算拆为两个**）

---

## 背景（2026-09-25 实测：弱网 / 大上下文「首字符一直回不来」）

`ProviderConfig.timeout`（默认 60s）**一个值同时承担四处职责**：

| 落点 | 覆盖的阶段 |
|------|-----------|
| reqwest `read_timeout`（`build_http_client`） | 等响应头 + body 字节间 |
| 流式 producer `read_idle`（`chat.rs` 循环） | 响应头之后：**首个字节** + 块间字节间 |

长上下文预填充（上游在算 prompt，数十秒~数分钟无任何输出）与弱网首包，会被
60s 预算当成「空闲」误杀 → 重试再被杀（每次重试重新预填充）→ 用户观感即
**「首字符一直回不来」**。反向也不能靠调大 `timeout` 解决：provider 挂死的
检测同时变慢（块间空闲是"应该很快"的信号，等 300s 才发现挂死不可接受）。

**判据**：两种等待的性质不同——
- **首 token 等待** = 上游在**计算**（预填充），慢是正常的，预算应大；
- **块间空闲** = 上游在**产出**中途停止，慢即异常，预算应小。

---

## 决策

### 1. 配置面：两个字段

- `ProviderConfig.timeout`（默认 60）——语义**收紧**为**块间空闲**：
  相邻数据块之间允许的最长无数据间隔（非总时长，流式长输出不受限）。
- `ProviderConfig.first_token_timeout`（**新增**，默认 300，校验 1..=3600）——
  **首 token 预算**：「请求发出 → 首个字节 / 事件」的最长等待。

### 2. 流式 producer：分两段判定

首字节前用 `first_token`，首字节到达后切回 `read_idle`（流式心跳 / 增量会
重置它——provider 持续发心跳即证明"活着"，这正是 keep-alive 的用途）。

错误消息必须区分（可观测性）：
- `模型服务错误：首 token 超时（Ns 内无任何输出——预填充超预算或服务不可达）`
- `模型服务错误：流式读取空闲超时（Ns 无数据）`

### 3. 传输层兜底：`read_timeout = max(首包预算, 块间空闲)`

reqwest 的 `read_timeout` **同时约束**「等响应头」与「body 字节间」，且不是
我们能精细控制的分段判定——它必须取两者中**更宽**的值作**兜底**，否则会在
显式判定之前先掐断长预填充（表现为 `error sending request` / 读超时类错误）。
精细判定归流式循环（§2），兜底只防"彻底无进展"。

---

## 替代方案与否决理由

| 方案 | 否决理由 |
|------|---------|
| A. 只调大 `timeout`（如 300s 统一） | 挂死检测变慢 5 倍；且把两种性质不同的等待混在一个旋钮上，用户无法分别调 |
| B. 按输入 token 数动态计算首包预算 | 预填充耗时与 provider/负载/量化都相关，token 数不是可靠预测因子；固定 300s + 可配已经覆盖实测场景（弱网 + 大上下文 < 5 分钟） |
| C. 首包也靠 SSE 心跳保活（有心跳即重置） | 部分网关在预填充阶段**完全静默**（无心跳）——必须有不依赖心跳的首包预算 |

---

## 后果

**正面**
- 弱网 / 大上下文预填充不再被误杀（首字符能等到）；
- provider 挂死仍能在小块间空闲预算内被发现；
- 错误消息可区分两类故障（用户/排障直觉不同：一类"等一等能成"，一类"得换服务"）。

**成本 / 负面**
- 配置面 +1 字段（默认值合理，旧配置零迁移——serde 默认 300）；
- 传输层兜底取 max 后，**非流式**请求（embedding / vision）的读空闲也放宽到
  首包预算（300s）——挂死检测变慢，但由显式逻辑与上游超时共同兜底，可接受。
