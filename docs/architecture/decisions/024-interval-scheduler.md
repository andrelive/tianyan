# ADR-024: 调度模型从 cron 改为间隔 + 补跑

- 状态：已采纳（Accepted）
- 日期：2026-08-31
- 关联：ADR-013（统一消息通知与唤醒）、ADR-017（演化任务降频）

## 背景

0.2.4 验证暴露的调度缺陷：

1. **服务不常驻假设不成立**：cron「某时刻执行」默认进程一直活着。个人 PC 上
   服务随应用开关机，错过的 cron 触发永不补跑——用户设定的「每天 09:30」
   在宕机日整天不执行；内置摘要任务同理。
2. **UTC 语义触发时刻漂移**：`cron` crate 按求值上下文解析，`0 0 */6 * * *`
   实际在 UTC 0/6/12/18 点触发 = 本地（UTC+8）8/14/20/2 点——用户感知为
   「时间这么整的奇怪时刻」（8/29 20:00、8/30 20:00、8/31 14:00 三次整点
   闪退均发生于该触发时刻）。
3. **双跑 bug**：`next_delay_secs` 用 `num_seconds()` 向零截断，边界后
   0.01s 算出 0s（max(1) 修成 1s）、边界前 59.01s 算出 59s——每个任务在
   整点 ±1 秒各执行一次（usage_stats_flush 每分钟跑两次）。
4. 内置维护任务的 `last_run` 仅存内存，重启清零，无补跑依据。

## 决策：间隔 + tick 扫描 + 串行执行

1. **任务定义**：`TaskDefinition.interval_secs: u64` 取代
   `cron_expression`。语义：距上次执行完成 ≥ interval_secs 即到期，
   下个扫描周期立即执行。
2. **单一扫描循环**：废除每任务一个 cron 循环，改为单一扫描循环每 tick
   （默认 60s）按注册顺序检查全部任务，到期的逐个**串行**执行——维护任务
   （LLM 调用 / LanceDB / SQLite）天然避免并发争抢，不再需要并发信号量。
3. **last_run 持久化**：`{data_dir}/scheduler_state.json`（id → last_run +
   run_count），启动时加载、每轮扫描后落盘。宕机超期的任务重启后**补跑一次**
   （单次补跑，不回放错过的次数——防积压爆炸）。首次注册的任务视为到期
   （首跑在下一个 tick）。
4. **全站统一**：内置维护任务（summary 6h / gc 6h / snapshot_gc 12h /
   usage_stats_flush 60s / reminder 读取 reminder.interval_secs / evolution
   读取旧 cron 换算，无法换算回退 24h 并告警）与用户自建定时智能体任务
   （scheduled_agent_tasks.json）共用同一模型。用户任务旧 cron 字段在 load
   时自动换算（`interval_from_cron`：*/N 秒、*/N 分钟、每天 H:M → 86400）
   并回写迁移结果；换算失败回退 86400 + 告警。
5. **schedule_task 工具**：参数 cron → `interval_secs`（最小 60）；
   GUI「定时任务」创建表单从 cron 输入改为间隔预设（30 分钟/1/6/12 小时/
   每天/每周/自定义）。
6. `evolution.cron` 配置字段弃用（保留兼容读取），日志提示删除。

## 后果

- 正面：宕机必补跑（核心诉求）；UTC 漂移、双跑、时钟对齐问题整体消失；
  调度器代码量减半（单循环替代 N 循环 + cron 解析）；串行执行消除资源争抢。
- 代价：墙钟语义丢失——「每天 09:30」变为「每 24 小时一次（时点漂移）」，
  对个人 PC 维护类任务可接受；统计刷盘/提醒的触发精度受 tick（60s）限制；
  旧 cron 配置仅做尽力换算。
- 否决方案：保留 cron + 错过补跑（anacron 式）——需要持久化下次触发时刻、
  仍存在 UTC 语义与双跑问题，复杂度换不来收益；仅内置任务改间隔、用户任务
  保留 cron——两套调度语义并存，心智与代码双份成本。
