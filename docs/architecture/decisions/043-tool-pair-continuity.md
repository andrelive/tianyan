# ADR-043: 组装层工具对连续性规范化

**日期**: 2026-09-24
**状态**: ✅ 已落地
**修订**: ADR-035 §8（「不切开工具对」从**分页视图**扩展到**请求视图**）
**修订（2026-10-20）**: 悬空调用从「移除」改为「保留 + 补 id 对齐的合成结果」——
原做法会让合成结果变成孤立 tool，被严格上游拒绝（见文末「修订记录」）
**影响范围**: 上下文组装（`core/src/context/assembler.rs`）、压缩判定
（`core/src/agent/agent_core.rs` 的 `conversation` 构造）

---

## 背景（2026-09-24 全库实测：37522 条消息）

上游（OpenAI 兼容协议）硬要求：assistant 消息带 `tool_calls` 时，其**紧随**的消息
必须是对应的 tool 结果。实测天演链上有两种断裂：

| 形态 | 实测规模 | 机制 |
|------|---------|------|
| **插队** | 89 处 | 长工具执行期间（实测数十秒）异步通知（system）或用户消息落库，插在 `assistant(tool_calls)` 与 tool 结果之间（例：`… 16:34:13 assistant(tool_call) → 16:34:20 system"[后台服务就绪]" → 16:34:58 tool(结果)`） |
| **中断残留** | 11 处（调用悬空） | 工具被中断（用户停止 / 进程中断）→ 结果永不落库，调用悬空；用户接着发新消息（`… assistant(tool_call) → user"怎么中断了？继续"`） |

**后果**：请求被上游拒（`An assistant message with 'tool_calls' must be followed by
tool messages`），且**错误链常驻**——该会话此后**每次**请求都失败（0.5.x 实测日志：
同一会话连续多条 400；ADR-036 的结构性取消并不修复链，只让轮更早退出）。

**机制缺口**：`ContextAssembler` 只做「逐条转换」（`structured_to_messages`），
**不校验跨条的工具对连续性**——ADR-035 §8 只在**分页视图**做了「页首对齐 user
消息」，请求视图没有对应保护。

---

## 决策

### 组装层的单点规范化：`normalize_tool_pairs`

在组装层（StructuredMessage → Message 的**唯一入口**）做幂等的链规范化：

1. 已存在的 tool 结果**提前**到其调用之后（其余消息相对顺序不变）；
2. 悬空调用：**保留**在 assistant 上（`tool_calls` 原样），并**补一条 id 对齐的
   合成 tool 结果**（`[结果] 工具调用被中断，未产生结果`）——让模型看到「调用发生
   过、被中断」的事实；
3. 无任何调用认领的**孤立 tool 结果**丢弃（同样触发上游 400）。

**只作用于请求视图**：库与缓存不动，无数据迁移；结果确定（同一链每次同一视图）
→ 前缀缓存不受影响（ADR-012/030 的前缀零漂移语义保持）。

调用点两处（都发往同一上游，都必须合规）：
- `assembler::assemble` 的历史链组装；
- `maybe_compress_and_persist` 的 `conversation` 构造（压缩摘要请求本身若带断裂链，
  压缩会 400 → 会话卡死）。

---

## 替代方案与否决理由

| 方案 | 否决理由 |
|------|---------|
| A. 落库层修：通知落库时「有未闭合 tool_calls 则挂起，结果落库后再 flush」 | 通知来自异步 watcher（后台任务/命令终态），需要跨模块的挂起队列 + 时序状态机；ADR-035「简单正确优先」——组装层一次转换即可根治，且不改库 |
| B. 存量清洗（改写 89 处链） | 治标：新断裂会继续产生；且改写库要动历史事实（快照/undo 语义受影响）。组装层规范化对存量与增量**同时**生效 |
| C. 只在悬空时丢弃调用（不补合成结果） | 模型看不到「上次调用被中断」，倾向于凭空重试同一动作；补合成结果更接近真实语义 |
| D. 在 `ChatMessage` 展示层修（前端） | 展示层不是请求层——400 发生在请求组装，展示层修复对上游零影响 |

---

## 后果

**正面**
- 「孤立 `tool_calls` 链 → 会话永久 400」在结构上不可能（请求视图恒合规）；
- 无数据迁移、无新存储、无新抽象——沿用组装层既有的「归一」先例（压缩点 system → user）；
- 与 ADR-035 §8 的分页视图保护同源同向，两条视图都不会切开工具对。

**成本 / 负面**
- 组装每轮多一次线性扫描（`HashMap` + 两遍遍历，链长量级为压缩点后段，成本可忽略）；
- 合成结果消息带 `synth-{call_id}` 前缀 id、**不落库**——前端/导出不可见（有意：
  它是请求视图的补丁，不是会话事实）。

---

## 验收（判别力测试）

`core/src/context/assembler.rs`：
1. 插队重排（形态 A：结果提前、通知后移，且提前的是**同一次**调用的结果）；
2. 悬空补合成结果（形态 B：调用**保留** + `tool` 消息补齐 + 用户消息顺序不变）；
3. 孤立结果丢弃；
4. 一次调用多工具、部分有结果（保留有结果的、悬空补合成）；
5. 规范链不被增删（顺序/数量不变）+ **幂等**（二次规范化结果一致）；
6. 端到端 `assemble`：任意断裂链产出的序列满足「assistant(tool_calls) 后紧邻 Tool」。

**注入旧行为（跳过规范化）→ 第 1/2/3/6 条必红。**

7. **反向断言**（2026-10-20 补）：每条 `tool` 消息的 `tool_call_id` 必须属于紧邻其前
   assistant 的 `tool_calls`。**注入「删掉悬空调用」的旧行为 → 第 2 条与本条必红**
   （此前只有前向断言，缺这一条，于是把错误形态固化成了期望）。

## 修订记录（2026-10-20）：悬空调用改为「保留」

**症状**：opencode（zen/go，转发 DeepSeek 官方上游）调用 `deepseek-v4.1-flash` 时，
会话每次请求都 400 —— `Messages with role 'tool' must be a response to a preceding
message with 'tool_calls'`；换 ollama.com 同名模型却正常（其 OpenAI 兼容层不校验
工具对，把消息直接拼进 prompt）。

**根因**：原实现（第 2 点）「从 assistant 上移除悬空调用 + 补合成结果」自相矛盾——
补出来的 `tool` 消息带着已被删除的 `tool_call_id`，必然无人认领。上游两个方向同时
约束（**每个调用都要有结果** / **每条结果都要能找到调用**）：删调用满足了前者，
撞穿了后者。

**实测（2026-10-20，全库 84 会话 / 6 万条消息）**：

- 库内**孤立** tool 结果 = 0；**悬空调用** = 12 处（6 会话，均为中断/取消/并行丢结果）；
- 按原实现生成的请求视图：4 个会话违规，**全部**是「tool 无前置调用」方向
  （例：`sched-task-…` 视图第 4/5/6 项 = assistant 被删空 + 两条合成 tool；
  `session-265f5896-…` 链尾中断残留）；
- 按本修订生成的视图：上述会话违规全部归零（逐个复算）。

**影响面**：存量会话**无需清洗**——库内没有孤立结果，只有真实发生过的「调用无结果」；
请求视图每次重算，修复对存量与增量同时生效（ADR-043 原本的「库不动」原则不变）。
压缩请求走同一套规范化，因此「会话既不能继续也不能压缩」的卡死一并解除。
