# ADR-055: 快照排除边界与回退删除护栏

**日期**: 2026-11-11
**状态**: ✅ 已采纳（已实施）
**影响范围**: 快照模块（`core/src/snapshot/mod.rs` 树格式 v2 + 排除规则 + 删除护栏 +
空目录清理、`core/src/snapshot/redo.rs` 同源复用）、回退编排
（`core/src/agent/rollback.rs` 结果回报）、桌面端（`gui-native/src/sessions.rs`
回退提示）

---

## 背景

2026-11-11 只读诊断（数据目录实测）暴露三个互不相同、但同源于「快照边界没有明确定义」
的问题：

1. **空间**：数据目录约 8 GB，`snapshots/` 占 6,729 MB（84%；db 933 MB、lancedb
   202 MB）；快照内 `objects/` 4.5 GB、112 个会话目录、**110,406 个文件**，最大单
   会话 718 MB。
2. **排除规则只有 4 个目录名**（`.git` / `node_modules` / `target` / `snapshots`），
   **不读 `.gitignore`**。实测某会话 9,462 个快照文件里 4,935 个是 Playwright 截图，
   另有 `.vitepress/cache`、`dist-old` 等构建产物——它们全都写在 `.gitignore` 里。
3. **回退的删除范围没有边界**：`restore_tree` 的第三步是「删除目标树中不存在、但当前
   工作区存在的文件」，前提是「当前工作区扫描结果 − 目标树 = 回退点之后新增的文件」。
   该前提在四种情况下不成立（见下表），旧实现无任何校验——最坏会清空工作区。

| 破绽 | 触发条件 | 旧实现的后果 |
|------|----------|--------------|
| 工作目录漂移 | 快照捕获在 A 目录，回退时绑到 B 目录（ADR-015 允许 `with_workdir` 任意绑定） | **B 目录全部文件被删** |
| 空树 | 树文件损坏但仍可解析（`{}` 是合法 JSON）、锚点树从未捕获 | **工作区全部文件被删** |
| 属主不明 | 文件在捕获时未纳入（`.gitignore` / 超 2 MB / 读取失败），回退时纳入了扫描 | 该文件被删 |
| 规则漂移 | 排除规则在捕获与回退之间变化（用户改了 `.gitignore`） | 同上 |

同期的参考实现对账（opencode 源码 + 事故 PR `#47861`）：它同样用「扫描 − 树」判定删除，
但加了**路径归属校验、owner 校验、`maxDeletions = 100`**——起因是真实事故：一次 revert
在 5 秒内删掉 421 个文件。天演此前只有「删除」这一步，没有任何一层。

附带一个性能事实（同一次诊断）：`restore_tree` 遍历两遍——`walk_current`（1,017 个
文件，带排除，418 ms）+ `prune_empty_dirs`（**无排除**地扫 1.8 万个目录，含
`target/`、`node_modules/`），且**零文件变更时也照跑**。这是「明明这一轮没产出物，
回退也要好几秒」的主要来源。`prune_empty_dirs` 另有语义问题：它会删掉工作区里
**原本就存在**的空目录（用户有意保留的占位目录）。

---

## 决策

### 1. 树格式升到 v2：把「归属证据」落盘

`trees/{key}.json` 与 `redo/tree-{key}.json` 从裸 `{相对路径 → sha256}` 改为：

```json
{
  "workdir": "F:\\work\\git\\tianyan",
  "files": { "src/main.rs": "…" },
  "skipped": ["dist", "node_modules", "debug.log", "big.bin"]
}
```

- `workdir`：捕获时的工作目录（`fs::canonicalize` 结果）——证明这棵树属于哪个目录；
- `skipped`：**捕获时存在但未纳入快照**的路径（内置排除 / git 忽略 / 超 2 MB /
  读取失败）。目录只记目录自身一条，匹配时按祖先前缀命中。

两者缺一，恢复侧就只能靠数量上限兜底。解析入口**只有一处**（`parse_tree_file`，
serde `untagged` 兼容 v1 裸 map）：restore / diff / redo / GC 标记全部经它，
避免版本差异散落到调用方各自漂移——GC 曾因直接按 `SnapshotTree` 解析而在 v2 树上
永久跳过清扫。

### 2. 删除前过护栏（`deletion_plan`，纯函数可单测）

按代价从低到高逐条否决，任一命中即**抑制删除**：

| 判定 | 条件 | 处置 |
|------|------|------|
| 空树 | `files` 为空、候选非空 | 全部保留 |
| 归属不符 | 树记录的 `workdir` ≠ 当前恢复目录 | 全部保留 |
| 属主不明 | 候选命中 `skipped`（祖先前缀匹配） | 该候选保留 |
| 数量超限 | 剩余候选 > 上限（v2 树 5,000 / v1 树 200） | 全部保留 |

**抑制删除 ≠ 中止回退**：文件写回照做，只是多留几个文件。这一点是刻意的——中止会
把「用户明确点的回退」变成失败操作（消息链不截断、文件也不动），而抑制的代价只是
工作区多几个文件、用户可手工清理。**任何情况下都不丢数据**是这里的第一目标。

抑制必须**回报到前端**：`RestoreReport { written, deleted, deletion_suppressed,
suppression_reason }` → `RollbackOutcome` / `RedoOutcome` 同上字段 → 桌面端在
`deletion_suppressed > 0` 时给出「回退了，但 N 个文件按护栏保留：原因」。用户不知道
「文件没回退干净」比多留文件更糟。

### 3. 排除规则加第二道：读 `.gitignore`（调 git，不自研解析）

遍历前一次性取回被忽略清单：

```
git -C <workdir> ls-files --others --ignored --exclude-standard --directory -z
```

- `--others` 限定未跟踪文件（已跟踪文件不受 `.gitignore` 影响，这正是 git 语义）；
- `--exclude-standard` 覆盖 `.gitignore`（含嵌套、`!` 取反、`**`、路径锚定）+
  `.git/info/exclude` + 全局 excludesfile；
- `--directory` 把整棵被忽略目录折叠成一条 → 命中目录在遍历时**整棵剪枝**（体积与
  遍历成本的双重收益）；
- 非 git 仓库（无 `.git`）/ git 不可用 / 超时（3 s）/ 非零退出 → 空清单，只用内置
  排除，**绝不阻断快照**。子进程经 `hide_console_window`（与 `rg` 调用同一套平台旗标）。

### 4. 空目录清理收窄到「本次删除的父目录链」

只从「本次真正删掉文件的父目录」出发逐级向上 `remove_dir`（非空即失败、忽略）。于是：
不遍历整棵工作区（复杂度 = 被删文件的父链），**且绝不删工作区原有的空目录**。

### 5. 存量树重写（`tools-ops` 的 `prune_snapshot_trees`）

前四条只对**新**快照生效。存量树仍引用着被排除的对象——GC 不敢回收，磁盘一分不减。
因此配一个运维工具，按**与项目无关的通用排除集**重写存量树（`trees/*.json` 与
`redo/tree-*.json`，排除 `*.cache.json` 与 `redo/messages-*.json`——后者是被回退的
消息本身，不是树），把命中路径从 `files` 里剔除、折叠后并入 `skipped`。

在真实库执行（2026-11-12 `D:\tianyan`）：

| 观测 | 数值 |
|------|------|
| 树文件 | 2,427 个（2,008 MB） |
| 条目 | 14,396,416 → 10,904,827（剔除 3,491,589 = **24.3%**） |
| 树体积 | 2,007.7 → **1,550.6 MB**（-457 MB，耗时 151 s） |
| 孤儿对象（GC 待回收） | **24,748 个 / 343.7 MB**（活对象 82,458 个 / 4,165.6 MB） |

规则：目录名 `target` / `node_modules` / `dist` / `dist-old` / `coverage` /
`test-results` / `playwright-report` / `.playwright-mcp` / `.next` / `.nuxt` /
`.turbo` / `.cache` / `__pycache__` / `.pytest_cache` / `.venv` / `venv` / `.idea` /
`.omo` / `.trae` / `.git`；复合路径 `(.vitepress, cache)`；后缀 `.log` / `.msi` /
`.wixpdb` / `.tsbuildinfo` / `.db*` / `.pyc`。`--aggressive` 额外剔 `build` / `out` /
`.vscode` 与 `*.map`（这些目录可能被跟踪，默认不动）。

为什么是通用特征集而不是 `.gitignore`：旧树是 v1、**不记录工作目录**，无法按会话
解析 `.gitignore`。因此覆盖不了项目特有忽略项（例如本仓库 `.gitignore` 单独列的
`docs/naming-decision.md` 不会被剔）——刻意的保守取舍：宁可少删（留下无害条目），
不可误删用户内容。

格式沿用原样：v1 树写回仍 v1（**不为旧树编造 workdir**——写错会让回退删除被全量
抑制，比「无信息 + 数量上限」更糟），原本带 `workdir` 的树写回 v2。语义变化明说：
被剔除的路径**不再参与回退**（既不恢复也不删除），消息链回退不受影响。

`--gc` 探测 `127.0.0.1:3000`，服务在监听就拒绝执行：标记-清扫与运行中的捕获有竞态
（对象已写、树未落盘时会被判成孤儿）。重写本身不需要停服务（原子写；最坏情况是
某棵「最新树」被通用规则版覆盖，下一次捕获写回精确版）。

## 拒绝的替代

| 替代 | 否决理由 |
|------|----------|
| 删除数超限直接中止整次回退 | 用户显式点的回退变成失败操作（链不截断 + 文件不动），可用性代价远大于「多留几个文件」 |
| 只在删除后弹确认框（二次确认） | 需要新增 API 参数与前端交互闭环；而真正的风险场景（工作目录漂移、空树）应无条件拒绝，不该交给用户确认 |
| 自研 `.gitignore` 解析 | 语义细节多（嵌套文件、`!` 取反、`**`、路径锚定、`info/exclude`、全局 excludesfile），自研实现必然与 git 漂移 |
| 引入 `ignore` crate | 能覆盖 `.gitignore` 但不覆盖 `.git/info/exclude` / 全局 excludesfile 与「已跟踪文件不受忽略」的 git 语义；且给 core 增加一条仅此处使用的依赖 |
| `git check-ignore --stdin` 逐路径判定 | 需要先把所有路径枚举出来，失去目录级剪枝（而剪枝正是空间收益的主要来源） |
| 继续用「裸 map」树文件 + 只加数量上限 | 无属主证据时上限只能压到保守值（否则正常大回退被挡），等于把边界问题降级为概率问题 |
| 存量清理改成「按时间删旧快照」 | 收益同量级（30 天前的树占 82%），但会**丢掉那些历史锚点的文件回退能力**；重写保留能力，只是被忽略的路径不再参与 |
| 重写存量树时读 `session_meta` 拿 workdir 升 v2 | 能让旧树也带上归属证据，但引入数据库依赖与「workdir 已不存在/已改绑」的判定分支；收益只是把 legacy 上限（200）换成精确判定，不值得在这个一次性脚本里扩面 |

## 后果（诚实记账）

- **旧格式树（v1）在升级后仍然可用**，但没有 `workdir` / `skipped`：删除走 legacy
  上限（200）。存量树会在后续每轮捕获中被 v2 覆盖，属过渡态；回退到很久以前的锚点
  （旧树）时，若候选超过 200 个会全部保留并提示——这是保守选择，不是缺陷。
- **`skipped` 让树文件变大**：目录级只记一条，实际增量有限（实测工作区里通常是
  个位数目录 + 若干大文件/日志）。换来的是「删除有据」。
- **每轮捕获多一次 `git` 子进程**（实测 tianyan 仓库单次 100–200 ms）。清单按
  `workdir` 做进程内缓存（TTL 60 s、`Arc` 跨 `with_workdir` 克隆共享）——一次
  回退的三次遍历（`save_redo` / `restore_tree` / `diff`）只 spawn 一次；`.gitignore`
  的改动最多延迟一个 TTL 生效（不影响正确性，见上）。忽略清单生效后遍历与哈希的
  文件数大幅下降，净值仍是加速。
- **忽略目录里的改动不再进快照**：这是 `.gitignore` 的语义，也是期望行为
  （构建产物、截图、缓存不进快照）。用户的临时产物若需回退保护，应从 `.gitignore`
  里移除或放到被跟踪路径下。
- **抑制删除后工作区与快照树不一致**：下次 `diff` 会把这些文件显示为 `added`——
  这是事实，不做自动清理。

## 验收

- 新增单测 9 个：工作目录漂移、空树、`skipped` 命中、上限边界（纯函数）、
  `.gitignore` 不入树 + 记入 `skipped`（依赖真实 git，缺失即跳过）、v1 树兼容、
  v2/v1 解析判定、`path_under` 前缀口径、原有空目录保留。
- 运维工具单测 6 个：目录命中折叠到最浅一层、`.vitepress/cache` 成对判定（不误删
  同目录 `config.ts`）、后缀命中、源码路径不受影响、`--aggressive` 只扩展不改变默认、
  百分比除零。
- **反向注入验证**（每项改动注入旧行为，测试必须变红）：
  - 删除护栏改回「全放行」→ 4 个护栏测试红；
  - `git_ignored_paths` 改回空集 → `.gitignore` 测试红；
  - 空目录清理改回全树遍历 → 原空目录保留测试红。
  一次全注入：6 红，撤回后 50/50 绿；core 全量单测 1,234 通过。
