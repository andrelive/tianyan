# ADR-051: 桌面端单 server 复用（`desktop/` 启动编排段）

**日期**: 2026-10-27
**状态**: ✅ 已采纳（阶段 1 已实施；阶段 2 待定，见末尾）
**影响范围**: 新 crate `desktop/`（`tianyan-desktop`）、`core/src/common/path.rs`（新增）、
`server/src/lib.rs` 的 `/health`、`tauri/src/{lib,server}.rs`、`gui-native/src/main.rs`

> **后续状态（2026-10，不改本 ADR 的决策内容）**：tauri 壳已**冻结**并移出 workspace
> `members`（native/GPUI 成为主发布渠道）。因此本 ADR 的"两个桌面壳"前提只剩一个壳，
> 但**机制与结论完全不变**——`desktop/` 防的从来不是"两个壳"，而是「同一数据目录上
> 跑两个 server」（双击两次快捷方式、GUI + CLI server 并存，都会触发；且 tauri 版
> `/health` 缺 `service`/`data_dir` 字段正说明判据必须严格）。`desktop/` 现在是
> gui-native 的启动编排段，**不可删**。

---

## 背景

### 1. 两个桌面壳，两个内嵌 server

`tauri/`（Tauri + React，现役）与 `gui-native/`（GPUI，进行中）是同一产品的两个桌面壳，
各自内嵌一个 axum server，连同一个数据目录。

### 2. 端口探测只解决「端口冲突」，不解决「数据目录双写」

两个壳的启动编排此前各写一遍 `find_available_port`（首选 3000，被占则顺延）：

```text
desktop 版先起 → 占 3000、注册定时任务、写 D:\tianyan
gui-native 后起 → 3000 被占 → 顺延 3001 → 也注册定时任务、也写 D:\tianyan
```

**这不是推演，是实测**（2026-10-27）：机器上 `3000` 与 `3001` 同时有 server 在跑，
两个进程各跑一遍定时任务、并发写同一个 SQLite。

### 3. 现有「单实例」判定漏判

`tauri/src/lib.rs` 已有 `existing_instance_running`（第二实例直接退出，与
`tauri-plugin-single-instance` 构成双保险），但它**只探首选端口 3000**：gui-native
先起并顺延到 3001 时，它判定「无实例」→ 再起一个 server → 又是双写。

另外它只看 `/health` 是否 200 —— **任何本地服务都可能 200**，这证明不了
「这个端口上跑的是天演」。

---

## 决策

### D1. 抽 `desktop/`（`tianyan-desktop`）作为「启动编排段」，两个桌面壳共用

`find_available_port` / `start_axum_server` 从 `tauri/src/server.rs` 迁入（行为逐字保留），
新增发现与复用。它**只调 `tianyan_assembly::full()` 取插件清单，不直接 `use` 任何插件
crate**，因此 ADR-049 的「认识具体插件 crate 的只有三处」不变——它是装配器的启动编排段，
不是第二份装配清单。

### D2. 「已有实例」的判据是**两条都过**

`/health` 暴露身份（向后兼容，只加字段）：

| 字段 | 作用 |
|---|---|
| `service: "tianyan"` | 证明「这个端口上跑的是天演」，而不是碰巧返回 200 的本地服务 |
| `data_dir` | 证明「是我的实例」。数据目录是**可配置的**（ADR-023），一台机器上完全可能「主数据 / 测试数据」各跑一个天演——连错会读写别人的数据 |
| `pid` | 排查用：谁占着数据目录 |

### D3. `data_dir` 的比较口径收口到 `core::common::path`

`normalize_dir`：优先 `canonicalize`（解析 `..`/短路径/链接），失败退化为「统一分隔符 +
去尾斜杠」；Windows 转小写。`same_dir`：**空串一律判不匹配**——旧版 server 不报
`data_dir` 时宁可多起一个进程，也不猜。

服务端写 `/health` 与客户端比对**必须走同一函数**，否则口径漂移会让复用静默失效
（表现为第二个 server 照旧被启动）。

### D4. `ensure_server` 的语义

- 命中：`reused = true`。本进程**不启动** server，退出时也**不该关它**（否则会把另一方的
  server 关掉）。
- 未命中：绑定端口 → 装配 → 启动 → 等就绪。**就绪失败要把刚 spawn 的 server `abort` 掉**，
  否则留下一个「在跑但没人用」的 server，还会因其优雅关停而卡住进程退出。

### D5. 阶段 1：gui-native 复用，tauri 保持「发现即退出」

| 壳 | 行为 | 理由 |
|---|---|---|
| `gui-native` | 发现 → **复用**（连过去，窗口照开） | 迁移期要能和桌面版并存对比 UI |
| `tauri` | 发现 → **退出**（判定改为扫整段 + 校验 data_dir） | 单窗口语义已有 single-instance 插件兜底；改它的启动路径风险最高，留到阶段 2 |

### D6. 发现必须是「快路径 + 并发 + 预探」，并用测试钉住耗时上界

首次实现串行扫 101 个端口，单测跑了 **51.37 秒**（Windows 上这些端口是 DROP 不是 RST，
每个吃满 500ms 超时）。这在启动路径上等于「用户每次白等 50 秒」。三处修复后 **0.50 秒**：

1. **快路径**：先只探首选端口，命中即返回（绝大多数启动在这里结束）；
2. **并发**：其余端口 `JoinSet` 并发，最坏耗时 = 单端口超时上限；
3. **TCP 预探**：HTTP 之前 150ms `connect`，端口不活直接判否。

并加 `test_discover_existing_scan_is_bounded`（扫 101 个端口必须 < 5s）。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **第二实例直接退出**（对 gui-native 也用退出语义） | 迁移期无法同时开两个 UI 对比；用户裁决选「复用」（2026-10-27） |
| **写 `{data_dir}/runtime/server.json` 端口文件做快路径** | 生命周期管理（写/删/过期清理）+ 复用方不该删别人的文件，复杂度换不来收益；扫描已降到毫秒级。若将来端口段变宽再考虑 |
| **按数据目录加文件锁（独占）** | 锁只能「阻止第二实例」，不能「让第二实例用上已有 server」；且跨平台语义差异大（Windows 命名互斥 / Unix flock） |

## 后果与诚实边界

1. **旧版 server 不会被复用**：它不报 `service`/`data_dir`，客户端判为不匹配（宁可自己起
   一个也不猜）。桌面版升级到本版后自动生效——过渡期双写风险仍在，但只会出现在
   「旧桌面版 + 新 gui-native」这个组合上。
2. **复用方不负责关停**：谁起的 server 谁负责关。复用方退出时发的关停信号没有接收者
   （它压根没起 server），天然安全。
3. **同一数据目录 + 同一次启动**：若两个进程**同时**启动（毫秒级竞态），仍可能各绑到一个
   端口——发现逻辑在启动时只跑一次。彻底消除需要跨进程锁，本版不做（实际使用中窗口
   启动有先后，概率极低）。

### 教训（写下来防复犯）

- 「功能正常但资源白烧」先按**外部依赖**（子进程 / SDK / 网络客户端）分叉——MCP 忙循环
  那次按自己的模块分叉，两轮都空手（见 `CHANGELOG.md` 的 `[Unreleased]`）。
- **「只测端口活着」不等于「测了语义」**：旧测试起一个 `{"status":"ok"}` 的假服务就断言
  「探测到实例」，判定口径升级后它只能变假绿或假红。改法是让假服务**形状正确**
  （`service` + `data_dir`），并补一条「数据目录不同 → 拒复用」。
- 扫描类代码一律并发 + 预探，并把耗时上界写成断言。
