# 天演已知限制

> 长期有效的结构性限制（不含版本号、不含临时状态）。版本相关的已修事项见 [CHANGELOG](../CHANGELOG.md)。

本文不是 bug 列表，而是**会长期存在的形状约束**：要么是有意设计的代价，要么是外部环境（Windows / 模型行为 / MSI 语义）决定的边界。按影响程度分组。

## 影响：中

### 1. `apply_edit` 精确匹配的固有脆弱性

- **现象**：`apply_edit` 的 `old_string` 需**逐字节精确匹配**（含空行、缩进、行尾）。漏空行、抄错缩进、CRLF/LF 差异都会导致「未找到」。
- **现状**：已做行尾归一化（CRLF/LF 容差）+「未找到」报错带最近行提示；工具描述引导优先用 `apply_patch`（上下文锚定，更稳）。
- **限制**：内容匹配本质要求精确复现，模型偶尔仍会失败（报错后可纠正）。
- **处置**：报错即重试或改用 `apply_patch`；不会改错文件（未命中即不写）。

### 2. 数据目录只读：搬迁是唯一入口（ADR-023 §4）

- **现象**：设置页 `storage.data_dir` 字段是**只读**展示（右侧只有「复制」与「搬迁…」）；直接用 `PUT /api/v1/config` 改它无效 —— 服务端**丢弃**请求里的 `storage.data_dir`，以运行时值为准并记 `warn!`。
- **原因**：直接改配置会让下次启动在空目录里跑（旧库还在原处、服务看不到）= 用户视角「数据全没了」。安全语义放在契约层，不放在界面层。
- **处置**：换目录只能走「搬迁」入口（字段行按钮 → 目录选择器 → 确认框 → 整库复制 + 校验 + 切配置 + 删源）。选中 ≠ 生效，且不可撤销。详见 [ADR-023](architecture/decisions/023-config-data-dir-separation.md)。

### 3. 没有 CLI 交互模式

- **现象**：天演只有**桌面客户端**（`gui-native`，GPUI 原生；`gui-vite` 保留做对照）+ **HTTP API**。没有 `tianyan chat` 之类的命令行对话；命令行只用来传启动参数，不构成交互。
- **限制**：脚本化只有 HTTP API 一条路（端点见 [`api-endpoints.md`](api-endpoints.md)），需要自己起服务/起客户端。
- **处置**：要走自动化，用 HTTP API 或 GUI 自动化端口（ADR-052）。

## 影响：低

### 4. 模型生成截断工具调用（已护栏，未根治）

- **现象**：LLM 偶尔生成非法/截断的 JSON 工具参数，历史上曾导致整轮请求 400。
- **现状**：已加降级护栏（发送前校验，非法参数降级为 `{}`），不再 400 毒化整轮。
- **限制**：根因是模型行为（生成不完整 JSON），无法从源头避免；护栏兜住症状。
- **处置**：看到工具收到空参数，通常是这一条；重试即可。

### 5. 会话内规则/记忆不刷新（前缀冻结，ADR-012）

- **现象**：soul/rules/memories 前缀在会话**第一轮冻结**（快照），会话中途学到的规则/记忆**不注入当前轮**。
- **原因**：前缀零漂移以命中 DeepSeek 前缀缓存（省 token/延迟），是有意设计。
- **处置**：agent 可用 `search_vfs` 按需检索规则（Agent 命名空间）/记忆（Memory 命名空间）。单主题会话无感；长会话换话题时需主动检索。详见 [ADR-012](architecture/decisions/012-injectable-snapshot-persistence.md)。

### 6. 超大单行文件不适用行编辑

- **现象**：压缩后的 JS/JSON 单行（几百 KB）无法用 `apply_edit`（整行替换不现实），`read_file` 也受 50KB 字节预算限制。
- **处置**：用 `apply_patch` 按 diff 片段修改，或重新生成文件。

### 7. Windows 构建：`cargo test` 在 `opt-level=2` 下 rust-lld 崩溃

- **现象**：本机某些 profile 配置下（`opt-level=2` 的测试 profile），`cargo test` 的 rust-lld 崩溃（STATUS_ACCESS_VIOLATION）。
- **处置**：`CARGO_PROFILE_TEST_OPT_LEVEL=0` 环境变量绕过；`cargo build` / `cargo check` 不受影响。

### 8. 数据目录搬迁用 copy 而非 rename

- **现象**：迁移使用 copy 而非 rename（Windows 上 SQLite 文件可能被锁，无 `FILE_SHARE_DELETE`）。
- **限制**：极端情况下（如外部进程占用）旧目录可能残留被锁文件，需**手工清理**。
- **处置**：迁移后新目录数据完整可用；残留文件无害，确认无进程占用后手动删除即可（迁移结果的 `leftovers` 字段与日志会列出它们）。

### 9. 生成速度（tok/s）在「成团下发」的上游下会偏大

- **现象**：底部统计条的 tok/s 偶尔跳到几百甚至几千（实测样本：51 ms 窗口 / 329 token → 6451 tok/s）。
- **原因**：速度 = 输出 token ÷（总耗时 − TTFT），而部分上游把整段响应**攒完再一次性下发**（直连 `ollama.com` 实测：153 条 SSE 帧聚在两个时刻），纯生成窗口只剩几十毫秒。**不是天演缓冲**（provider 层是 `bytes_stream()` 逐块转发），也不是算错。
- **处置**：按实际窗口**照实显示**（不设下限——空着比偏大更难解释）。要判断真实吞吐，看窗口 ≥ 1 s 的样本；`/usage/recent` 同时给出 `ttft_ms` / `duration_ms` 可自行核算。

### 10. 压缩后是否自动续跑，取决于会话里有没有 active goal（ADR-053）

- **现象**：模型主动调 `compress_context` 压缩完，只有在**本会话有 active goal**（或存在未绑会话的全局目标）时才会自动继续跑；没有 goal 时会话就停在压缩点，跟一条普通回答结束一样。
- **原因**：续跑的判据是「目标是否完成」而不是「压缩了就该继续」——否则每次压缩都无条件再跑一轮，长会话会自旋烧 token。判据由模型自己维护（`goal` 工具标 `completed` 即结束）。
- **限制**：忘记建 goal 的长任务，压缩后需要用户再说一句才会继续；子代理是**一次性任务**，压缩后不续跑（它的生命周期本就到收尾为止）。
- **处置**：长任务开始就建 goal（系统提示里已写明这条）；需要跨压缩点长驻的子代理是另一套设计，目前没有。
