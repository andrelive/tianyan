# 代码库设计：深模块（词汇与判据）

**ID**: `codebase-design`

**版本**: 1.0.0

**描述**: 设计"深模块"的共享词汇与判据——大量行为藏在小小接口后面，放在干净的 seam 上，可经接口测试。

**状态**: 正式

## 适用场景

- 设计或改进一个模块的接口
- 寻找**深化机会**（把浅模块变深）
- 决定 seam 放在哪里、代码怎么更可测 / 更可导航
- 重构讨论需要无歧义语言时

## 使用说明

### 词汇（用这些词，别替换成 component/service/API/boundary）

- **Module（模块）**——有接口 + 实现的东西。刻意跨尺度：函数、类、包、跨层切片都算。
- **Interface（接口）**——调用者必须知道的一切：类型签名，还包括不变量、顺序约束、错误模式、必需配置、性能特征。
- **Implementation（实现）**——模块内部。
- **Depth（深度）**——接口上的杠杆：调用者（或测试）**每单位接口能驱动的行为量**。大行为 + 小接口 = **深**；接口复杂度接近实现 = **浅**。
- **Seam（接缝）**——不改动此处就能改变行为的位置；接口所在之处。seam 放哪儿是独立的设计决策。
- **Adapter（适配器）**——在 seam 上满足接口的具体物；描述**角色**不是内容。
- **Leverage（杠杆）**——调用者从深度得到的东西：一份实现回馈 N 个调用点、M 个测试。
- **Locality（局部性）**——维护者从深度得到的东西：变更、bug、知识、验证集中在一处。改一次，处处已改。

### 判据

- **删除测试**：想象删掉这个模块——复杂度**消失** = 它只是通道（浅）；复杂度**散到 N 个调用方重现** = 它在挣饭吃（深）。
- **接口即测试面**：接口设计好了，测试自然好写。
- **一个适配器 = 假设的 seam；两个适配器 = 真实的 seam**（只有一个实现时，seam 是想象出来的）。
- **深度优先于抽象**："已有链路不叠加抽象"（天演硬约束同款）——抽象只有换来杠杆 / 局部性才值。

### 探查信号（找深化机会时）

- 理解一个概念需要在很多小模块间来回跳？
- 模块**浅**——接口几乎和实现一样复杂？
- 为了让某些东西可测而拆出的纯函数，但真正的 bug 藏在**调用方式**里（无局部性）？
- 紧耦合的模块在 seam 上泄漏？
- 大面积无测试、或经现有接口很难测？

### 重构序列（爆炸半径大时）

**先让改动变容易，再做容易的改动**。宽重构（一个机械改动扇出全库）用 **expand–contract** 序列：先 expand（新旧形态并存）→ 分批迁移调用点（按爆炸半径分块，每块独立绿）→ 最后 contract（删旧形态）。对应天演"波次"实践。
